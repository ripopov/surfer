Inside Surfer · Waveforms and design metadata

Follow a waveform
back to its source.

A waveform tells you when a register changed. Its companion design database tells you where that register was declared. Open the recording once, then right-click a signal and choose Go to source.

Two files, one debugging document

Try pipeline.vtr or operators.vtr from examples/verilator. Each recording comes from a real Verilator simulation and has a matching .vdb, original SystemVerilog, and an FST recording from identical stimulus. Keep the companion and RTL beside the trace when moving these examples.

Native Surfer opens VTR from the command line, the file picker, or a dropped file with an accessible local path. It first checks for the same basename with .vdb, then .vdb.json, which the native Verilator backend writes. For pipeline.vtr, that means pipeline.vdb takes precedence over pipeline.vdb.json. It does not search for a generic design.vdb.json.

The companion is optional. A malformed or mismatched preferred companion produces a log diagnostic and leaves waveform viewing available. Surfer does not silently fall back to another design after validation fails. FST, VCD and remote recordings continue to use their existing loaders; they do not borrow a neighboring VTR's design metadata.

3 · Workspace

Views hold intent

A waveform tile displays selected signals. The Source Code tile stores a file, line and column. Replacing a trace replaces its design attachment; a failed or obsolete load cannot overwrite the current document.

The VTR adapter builds Wellen's typed hierarchy and loads requested native VTR signal histories on background workers. It preserves scope component names, HDL types, directions, packed ranges, aliases and enum translations without serializing a VCD file. The shared renderer accepts native histories, so VTR uses the same translators, cursor queries, edge navigation and waveform drawing as FST. VTR transaction streams also feed the existing transaction views; their additional event, stage and relation details remain attached to the immutable transaction container.

Keep data while a visible view needs it

Opening a recording reads its hierarchy, stream names and generator names. A waveform row requests its canonical signal history; aliases and shared lists reuse that history. Transaction rows request records that overlap their viewport, grouped by generator. Overlapping requests from multiple views are merged. A visible inspector can request one selected transaction independently of those rows.

Visible tiles

Describe demand

Waveform rows, memory arrays, framebuffer ranges and rendered parameter values identify the signals they use. Inactive tabs do not retain them.

Document

Share and retain

The document holds one history per canonical signal and the requested transaction payloads. Removing the last request releases the data and hidden tiles' disposable caches.

Worker

Load, then check

A worker reads selected histories or transaction windows and clears decoded reader caches. The document rejects results that belong to another recording or obsolete demand. Existing worker accessors remain valid until dropped.

Explore shared ownership

This illustrative model uses two views of signal q and two transactions in generator issue: transaction 1 spans 2–6, and transaction 2 spans 7–9. View A shows q and issue; view B shows q. Changes represent completed background requests, not a benchmark or the actual UI.

q is shared by views A and B. Window 0–3 loads transaction 1. Closing A releases transaction 1; q stays until B closes.

Signal histories cover their recorded lifetime. Transaction windows include whole overlapping transactions and their details, not clipped fragments. Hidden group rows release their demand. A worker may temporarily hold a history after its view closes; its result cannot restore that history to the document. Removing and re-adding a failed signal request permits a retry.

Names connect the two worlds

The VDB calls the first stage output top.u0.q; Verilator records it as TOP.top.u0.q. The companion's explicit mapping connects these names. Surfer reverses that mapping for navigation. It retains a signal's own declaration when available and uses its shared signal identity to resolve waveform aliases that have no separate declaration. It never guesses a match by suffix.

Right-click a displayed signal row and choose Go to source. Surfer opens or focuses the Source Code tile, highlights the declaration line and scrolls it into view once. You can then scroll freely. The header shows the filename and location; hover over the filename to see its full path. Relative RTL filenames resolve from the companion's directory, while absolute paths remain absolute.

The tile remembers which elaborated instance it shows the file for: Go to source passes the signal's owning instance, the schematic passes the selected block's instance, and a header control switches between instances of the same module. Without a language server the text renders plain. Missing source files appear as an error in the tile. The source text is not embedded in VTR or saved workspace state; the instance context is saved with the tile.

Read the source as the simulator saw it

A design database knows declarations and connections; it does not know every token of every file. Accurate coloring, clicks inside functions, case arms or interface bodies, and the generate branches an instance leaves untaken all need a real SystemVerilog frontend. Surfer therefore starts slang-server, a language server built on the slang compiler, for the loaded design. It runs as a separate process and speaks the Language Server Protocol over its standard streams; nothing of it is linked into Surfer or the browser build.

The server elaborates exactly the design that was simulated. The VDB companion carries an elaboration record written by the simulator frontend: the working directory, design files, include directories, defines and top module. Surfer turns that record into a build file, hands it to the server, and never asks the user for a project configuration. Sessions belong to the loaded design: replacing the recording replaces the server.

Server: text and syntax

Semantic tokens classify every token of a file from the compiler's own syntax tree and symbol resolution: keywords, comments, literals, macros, and identifiers with their kind, port direction and whether they are clocks. Definition and instance lookups resolve any position, including inside functions, case arms and interface bodies. A per-instance query lists the generate blocks that instance does not instantiate.

VDB and recording: identity and values

The design database maps an elaborated path such as top.g_lane[0].u.count to the recorded signal, and the waveform document supplies the value at the cursor through the same translators as the waveform rows. Parameters use their per-instance elaborated constant when the recording did not trace them.

Tile: joins on demand

The tile only reads caches. A missing entry issues one request; the reply arrives on the message bus and fills the cache or emits a follow-up action such as opening a file or adding signals. Nothing blocks the frame, and the tile degrades to plain text while the server is starting or absent.

Hover, ctrl-click, alt-click

Hovering a symbol asks the server for its declaration summary and for the elaborated paths the token denotes in every instance. Paths inside the viewed instance are preferred; each is shown with its value at the cursor. Ctrl-click opens the declaration and keeps the owning instance as context; on an instance name it opens the instantiated module in that instance; on a module name it opens the module in its first instance. Alt-click adds the recorded signals of the token to the waveform, all instances when the token belongs to a module instantiated more than once. Struct fields and unpacked array elements resolve to the aggregate the simulator recorded.

Ownership and failure

The session is disposable runtime state of the application, keyed by the loaded design; it is never saved. Semantic tokens, inactive ranges and hover answers are cached per file and per instance for the life of the session. If the server binary is missing, fails to start or exits, the tile header says so and the text renders plain; waveforms are unaffected. The binary comes from [slang] server in the configuration, the SURFER_SLANG_SERVER environment variable, or PATH. The browser build has no process support and always renders plain text.

What the tests prove

The pipeline exercises hierarchy, aliases, asynchronous reset, enable holds and a two-stage data dependency. The operators example exercises signed arithmetic, bit selection, enum metadata and instance arrays. Tests compare every recorded transition and all scopes, variable types, directions, ranges and enum maps against their independently recorded FST companions. Each pair must also render against the same reviewed image snapshot.

Further tests cover source navigation through an actual context-menu click, replacement by FST, loading a dropped VTR, moving a companion with relative sources, the .vdb.json fallback, and rejecting a mismatched preferred companion. These integration tests consume files from examples. The language-server tests replay recorded sessions with a real slang-server (examples/verilator/*.slang.json) through the production client, so they need no C++ toolchain: highlighting in an instance, switching instances, the hover tooltip with a value at the cursor, alt-click adding signals, and ctrl-click on a variable, an instance name, a function, an interface member and a module name. An ignored test regenerates the recordings against a real server. The features example (package, function, interface with modports, generate branches selected per instance, case statement, include file with a command-line define) exists for these tests. The server's own unit tests cover token classification, clock detection and the per-instance generate query. Supplemental transaction examples are generated by cargo run -p libsurfer --example generate_vtr_examples; the RTL pairs use generate.py. Run cargo test -p libsurfer --lib for the full native suite.

The native signal backend opens the hierarchy without decoding waveform histories. It loads requested signals and releases histories no longer requested by visible tabs. Late worker results cannot restore removed signals. Reader decode caches are cleared after each native load; an accessor already held by a worker remains valid until dropped. Transactions open as stream/generator metadata only. Visible transaction rows request overlapping records for their generator and viewport; overlapping requests are merged. A visible inspector also requests its selected transaction. Removing demand drops transaction payloads and details, and outdated results are discarded. Hidden tabs drop their drawing caches, and hidden waveform items drop their analog caches. No measured speed or memory improvement is claimed. Browser-only byte uploads and remote VTR loading are not implemented. The parity claim covers the committed simulator examples, not every possible FST facility. VDB driver tracing exists in the parent VTR tools; Surfer exposes source navigation and a schematic tile built from the VDB netlist.

Extension points are explicit: new transaction presentations can use the same generator/window requests; new design views can share a document's validated identity; a richer source service can add editor integration. Those are future work, not hidden behavior of the source tile.
